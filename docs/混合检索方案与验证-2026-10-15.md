# 知识库 BM25 + 向量混合检索

## 改进目标与范围

原先 `search_chunks` 只用 embedding 在 Milvus 中召回 Top-K，再做重排。精确型号、论文术语或编号如果未进入向量候选，重排无法补回它们。

现在 BM25 从同一集合、同一 `kb_id` 过滤范围内的全部片段文本建立倒排索引，独立取关键词候选，与向量候选按片段 ID 融合，再交给已有重排服务。BM25 的语料不局限于向量 Top-K。

```text
问题 ── embedding ── Milvus COSINE ── 50 候选 ─┐
     └─ 同一分词器 ── BM25 倒排索引 ── 50 候选 ─┤
                                              ↓
                              chunk ID 去重 + 等权 RRF
                                              ↓
                                     前 50 个进入现有重排
                                              ↓
                                  返回原 top_k（默认 10）
                                              ↓
                       原有权限过滤、版本绑定、原文定位和资产补齐
```

本次只调整共享知识库召回层。知识库搜索页、使用该入口的知识库问答和科研本地文献检索自动受益。六个 Agent 的配置、流程编排、Web/Crossref/arXiv 检索、写作审核、SSE、checkpoint、记忆检索及独立政策搜索服务保持原实现。

## 兼容性选择

仓库及此次实际连接的服务均为 Milvus 2.3.3。Milvus 原生 BM25 从 2.5 引入；直接采用它需要升级服务并增加相应 schema。本次采用应用侧 BM25，保留七字段集合、已有向量、片段 ID、入库格式和 PostgreSQL provenance 表，不需要重新上传或重新生成 embedding。

`pymilvus` 的最低版本调整为 2.3.3，使用该版本已有的 `Collection.query_iterator`，每批读取 256 条，仅请求 `id` 与 `content`。不采用 `offset + limit` 翻页，避免只扫描首批或碰到结果窗口上限后静默截断。

参考：[Milvus 原生全文检索版本说明](https://blog.milvus.io/blog/full-text-search-in-milvus-what-is-under-the-hood.md)、[PyMilvus 2.3.3 Collection 源码](https://github.com/milvus-io/pymilvus/blob/v2.3.3/pymilvus/orm/collection.py)。

## 默认参数及理由

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `RETRIEVAL_HYBRID_ENABLED` | `true` | 开启混合召回；`false` 恢复原向量 Top-K + 重排 |
| `RETRIEVAL_CANDIDATES` | `50` | 每一路的召回数量，至少等于调用方 top_k，最多配置 200 |
| `RETRIEVAL_RERANK_CANDIDATES` | `50` | 融合后送入重排的数量，至少等于 top_k，最多配置 200 |
| `RETRIEVAL_RRF_K` | `60` | 平滑两路排名差异，避免直接相加不同量纲的原始分数 |
| `BM25_K1` | `1.2` | 限制词语反复出现带来的分数增益 |
| `BM25_B` | `0.75` | 对较长片段做长度归一化 |
| `BM25_CACHE_TTL_SECONDS` | `60` | 索引缓存有效期；0 表示每次重建 |
| `BM25_CACHE_ENTRIES` | `2` | 每个服务实例最多缓存两个集合/过滤范围索引，LRU 淘汰 |
| `BM25_MAX_CHUNKS` | `50000` | 单个索引的片段数量预算 |
| `BM25_MAX_POSTINGS` | `2000000` | 单个索引的“词项－片段”记录预算，使用紧凑整数数组 |
| `BM25_BUILD_TIMEOUT_SECONDS` | `30` | 冷索引构建的检查期限；Milvus 单次 RPC 另有 10 秒超时 |

原 `top_k` 范围仍为 1–50。50 路候选是默认 Top-10 的五倍，可为精排提供更多选择，同时控制调用规模；它是合理的起始值，不表示已找到本数据集的最优值。`k1=1.2, b=0.75` 采用常见 BM25 参数起点，参考 [Lucene BM25Similarity](https://lucene.apache.org/core/9_9_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)。后续可通过固定问题集比较 Recall@K、重排延迟与费用来调节候选数。

分词使用现有依赖 jieba 的搜索模式，关闭 HMM，统一 NFKC 和英文大小写。保留 `IL-6`、`Qwen-2.5`、DOI 等完整标识及其组成词；不额外引入同义词扩展或修改问题。BM25 使用正值 IDF、词频饱和与长度归一化；无词项命中的片段不会混入关键词候选。

融合公式为 `rrf_score(d) = Σ 1 / (60 + rank_i(d))`，两路等权；每路去重后从 1 开始计排名。去重依据是片段 ID，不是文件名，所以同名文档不会互相覆盖。

## 返回契约与状态一致性

- `search_chunks` 仍提供 `results`、`reranked`、`warning`；内部新增 `retrieval_method` 用于区分混合与向量降级。调用参数保持兼容。
- `score` 保留余弦相似度含义，纯 BM25 命中的该字段为 `None`；已有前端允许空值并显示“不可用”。内部 `bm25_score`、`rrf_score` 和 `retrieval_sources` 独立保存，不冒充余弦分数。外部现有字段与原文定位逻辑不变。
- BM25 索引只缓存片段 ID 和词频统计；命中后使用相同集合/`kb_id` 范围和 Strong 一致性回查当前行。原文内容、文件名、文档 ID 和 chunk_index 均取自当前 Milvus 数据，再进入既有授权与 provenance 补齐。
- 上传 upsert、删除文档、删除集合和集合改名会使本进程对应缓存失效。失败但服务端可能已经接受的写入也会失效，避免继续使用已知旧索引。
- 构建期间发生本地修改时，通过代数检查拒绝发布该索引。同一实例最多一个构建任务，其他冷请求等待最多 1 秒后降级，避免积压多个全库扫描。
- 其他进程或外部工具的新增/更新，通过 TTL 到期后的首次请求重建可见。TTL 内关键词排名可能仍按旧词频计算，但返回内容会回查；已删除的关键词命中会被过滤。此方案没有跨进程即时索引同步。

## 异常行为与容量边界

关键词读取、分词或索引构建失败，以及超过片段/倒排记录/时间预算时，整个关键词分支降级，保留原向量候选与原重排预算。`warning` 明确说明关键词检索不可用；日志记录降级。不会将被截断的语料当作完整 BM25 索引。

重排失败、分数数量不符或含非有限值时，保留融合排名；若同时发生关键词降级，两条警告都保留。embedding 或向量服务失败仍按原有错误路径处理，不改为伪装成功的空结果。

该实现服务于本仓库单个知识库范围内的检索，首次查询或失效后有构建成本；两个缓存项不代表只允许两个知识库。超预算知识库会降级，不能将这套进程内索引解释为亿级文献检索方案。需要大规模常驻倒排索引时，应另行评估原生 Milvus BM25 或独立搜索引擎迁移。

30 秒是构建时检查的期限，当前进行中的 RPC 最多还可能等待其 10 秒超时，且单个片段分词只能在返回后检查；它不是整个检索请求的绝对响应时限。

## 启用和回滚

拉取代码并安装符合 `backend/requirements.txt` 的依赖后，重启后端即可使用默认混合检索，无需修改现有 `.env`；如需调参，只合并 `backend/.env.example` 中的混合检索项，不覆盖原凭据。

回滚只需将 `RETRIEVAL_HYBRID_ENABLED=false` 加入实际后端环境并重启，恢复原向量候选数量及重排方式。无需回滚数据或清理数据库。此次只提交源码与验证脚本，不替用户重启正在使用的业务服务。
