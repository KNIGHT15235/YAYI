## 两项失败的原因

原报告中的两项失败是同一原因的两个表现：`final weighted review has a valid score` 要求取得有效分数；`real review score equals weighted dimensions` 要求该分数等于五维加权值。模型连续两次给出非法维度，后端按已有保护逻辑保留报告、清除旧评分，返回 `quality_score=null`、空维度和 `quality_review_status=unconfirmed`，因此两项都失败。报告、图表、SSE 和 PostgreSQL 检查点均已生成，没有证据表明它们丢失了原本有效的评分。

进一步定位到：

1. 旧提示要求“极其严苛”“必须找茬”，容易把任务明确提供的合成算例判成幻觉，并把诚实的局限说明当成偏见。真实回答出现 `-1` 等不合法分值。先前非法 JSON 数值示例已修过，但仅修改提示词后的真实恢复测试仍为 9/11，证明还没有解决稳定性问题。
2. 原纠正提示没有反馈具体失败字段、原值和上次回答，第二次调用仍可能重复错误。JSON 对象输出也不等于五维结构及数值范围已校验；阿里云的 JSON Object 与 JSON Schema 模式有不同保证，本项目继续使用 JSON Object 和后端业务校验。[官方结构化输出说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)
3. 审核沿用 DeepSeek 配置。实测仅调整提示仍连续失败，因此将审核单独设为现有服务已使用的 `qwen-plus`，其他 Agent 配置不变。实际使用的阿里云服务端点、模型支持范围应以其文档为准，不将其他厂商同名 API 能力直接套用。[阿里云 DeepSeek API](https://help.aliyun.com/zh/model-studio/deepseek-api)
4. 首次 Qwen 反例测试发现：模型先给高分和通过判定，随后在事实核查解释中发现计算错误，却没有同步更新问题列表。现在调整为先复算及来源核对、再列问题、最后评分；后端对结构化错误状态与严重问题列表增加一致性校验。
5. 基类此前会缓存 HTTP 成功且非空的响应，但这不意味着评分业务校验成功。该缓存不是已观察失败的直接原因——日志中确有两次真实模型调用——本次仍让审核和纠正请求绕过缓存，避免以后复用非法审核输出。
