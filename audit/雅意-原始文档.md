```Python
    def __init__(self, llm_api_key, llm_base_url, search_api_key, model):
        *# 初始化6个Agent*
        self.architect = ChiefArchitect(...)
        self.scout = DeepScout(...)

        self.critic = CriticMaster(...)
        self.writer = LeadWriter(...)

        *# 构建LangGraph状态图*
        self.graph = self._build_langgraph()

    def _build_langgraph(self):
        workflow = StateGraph(ResearchState)

        *# 添加节点*
        workflow.add_node("plan", self._plan_node)
        workflow.add_node("research", self._research_node)
        workflow.add_node("analyze", self._analyze_node)
        workflow.add_node("write", self._write_node)
        workflow.add_node("review", self._review_node)
        workflow.add_node("revise", self._revise_node)

        *# 设置边和条件路由*
        workflow.add_edge("plan", "research")
        workflow.add_edge("research", "analyze")
        workflow.add_conditional_edges(
            "review",
            self._should_revise,
            {"revise": "revise", "complete": END}
        )

        return workflow.compile()
```

**\[M01\-Q13\]\[为什么使用JWT而非Session\]    **Session 是传统的服务器端用户状态管理机制。它的工作流程是：用户登录成功后，服务器生成一个唯一的 Session ID，把用户信息存在内存或 Redis 中并与该 ID 关联，然后通过 Cookie 把这个 ID 发给浏览器。之后每次请求，浏览器自动带上 Cookie，服务器通过 Session ID 查找对应的用户信息。这种方式的问题在于，服务器需要存储所有用户的 Session，在多台服务器部署时还必须实现 Session 共享（通常借助 Redis），这增加了系统的复杂度和维护成本。相比之下，JWT 是一种无状态的认证方案。它的存储位置在客户端（通常是 localStorage），不需要在服务器端保存任何会话状态。这使得系统天然适合分布式部署，不需要做 Session 共享，扩展性更好。在性能上，JWT 每次请求不需要查询 Redis 或数据库来验证身份，减少了网络和存储开销。使用上也更简单，前端只需要在请求头里加上 `Authorization: Bearer <token>` 即可。当然，JWT 也有自己的安全考量。由于 token 通常存储在 localStorage 中，它需要防范 XSS（跨站脚本攻击）。XSS 是一种安全漏洞，攻击者把恶意 JavaScript 代码注入到网页中，窃取用户数据。如果网站存在 XSS 漏洞，攻击者就可以用 JavaScript 读取 localStorage，偷走 token。为此，我们采取了相应的防护措施：对用户输入进行转义，不直接渲染 HTML；使用 HttpOnly Cookie 存储 token，让 JavaScript 无法读取；同时设置 Content Security Policy（CSP）来限制恶意脚本的执行。综合来看，JWT 在无状态、分布式部署、性能和实现简单性上更符合我们的需求，因此我们最终选择了 JWT 作为认证方案。

**\[M01\-Q15\]\[为什么使用异步而非多线程\]    **因为我们的任务是IO密集型的，无GIL限制，异步在单线程运行，没有GIL性能瓶颈，不需要创建大量线程、进程、FastAPI原生支持异步。多线程在 Python 里无法利用多核 CPU 并行计算，还是同样的速度，多个线程轮流执行。这是因为Global Interpreter Lock（全局解释器锁）。

|模型|适用场景|性能|复杂度|
|---|---|---|---|
|同步|简单任务|低|低|
|多线程|CPU密集|GIL限制\(伪并发\)|中|
|多进程|CPU密集|高\(真并发\)|高|
|异步|IO密集|高|中|

**\[M01\-Q21\]\[为什么不全用开源LLM \(如Llama\)?\]   **开源LLM部署成本高\(需GPU服务器\),维护复杂\(模型更新、优化\)。闭源API按需付费,更灵活,且Deepseek性价比已经很高。

**\[M01\-Q22\]\[能否支持离线部署?\]    **可以,但需要替换组件:  LLM: 部署本地Llama/Qwen模型；搜索: 爬取数据建立本地索引；嵌入: 部署本地BGE模型。

**\[M01\-Q23\]\[多用户并发性能如何?\]   **单机支撑200\-300并发研究\(取决于服务器配置\)。如需更高并发:使用消息队列\(Celery\)异步处理；水平扩展多个Worker节点；使用负载均衡分发请求

## \[M02\-T03\] \[Agent \- DeepScout\*\*\*\]

**\[职责\]    **全网穿透搜索（不只看摘要，深入阅读原文，支持支持 trafilatura、BeautifulSoup、正则三种策略提取网页正文）；递归追踪（发现新线索自动深挖）；信源评级（评估来源可信度0\-1）；去重机制（基于语义指纹的事实去重）；假设验证（寻找支持或反驳研究假设的证据）；知识图谱（自动构建实体关系图）；网络本地双模搜索；补充搜索

**\[Prompt设计\]  ：**SEARCH\_ANALYSIS\_PROMPT（角色，输入定义，任务，输出，fewshot/特殊标准/特殊说明，用于分析搜索结果并提取结构化信息）；DEEP\_READ\_PROMPT（用于深度阅读长文本，网页正文，提取文档摘要、关键事实、数据表格、重要原文引用）；补充搜索分析 Prompt（用于分析补充搜索结果（CriticMaster 审核后发现信息缺失时使用））；深度搜索分析 Prompt（用于分析递归搜索的结果（信源追溯或线索追踪））

**\[核心实现\]：**

1. process\(\)入口：首先路由判断（正常研究\+补充搜索双模式路由）；然后是准备工作，尝试获取股票数据，更新状态为“研究中”，读取搜索配置（网络/本地），筛选出所有pending章节；向系统发送出一条“信息检索开始”的通知，附带进度统计；asyncio\.gather\(\)多章节并行搜索，从pending章节中每次最多取3个；发送完成事件，所有搜索任务跑完后，发送“检索完成”的通知，并统计结果数量和来源数量，最后触发搜索结果事件并返回状态，配合SSE实时事件流。

2. asyncio\.gather\(\)实现：首先准备配置，从章节中获取搜索词列表，并读取当前是本地搜索还是网络搜索；逐词搜索，若开启网络搜索，调用 `_execute_search` 拿结果，立刻通过 `add_message` 向前端推送当前进度和增量搜索结果（供 UI 实时展示），若开启本地搜索，同样调用本地检索并推送；把所有搜索结果交给 `_analyze_search_results` 进行大模型分析（提取事实、验证假设）；遍历 LLM 返回的`extracted_facts`，进行去重检查，将新事实和关联的数据点写入 `state["facts"]` 和 `state["data_points"]`；如果未达迭代上限可以递归深挖，信源追溯（最高优先级）：如果分析结果里有 `source_tracing_queries`，调用 `_execute_deep_search` 去追溯原始信源。线索追踪：如果分析结果里有 `follow_up_queries`，同样调用 `_execute_deep_search` 去追踪新发现的线索。每个 `_research_section()`  是一个独立的协程，同时执行，提升效率。

3. 信源可信度评级算法：评分标准在prompt中预设，官方来源0\.9\-1\.0，学术来源0\.8\-0\.95，权威媒体0\.7\-0\.85，行业报告0\.7\-0\.9，一般新闻0\.5\-0\.7，自媒体0\.2\-0\.5，LLM 根据 `source_name` 和 `source_url` 判断类型，输出 `credibility_score`自动评分

4. 交叉验证机制：\_compute\_fact\_fingerprint\(\)计算事实的语义指纹用于去重（提取数字和关键词作为指纹，拼接后计算MD5哈希，相同指纹认为是重复事实）；\_is\_duplicate\_fact\(\)检查事实是否重复（先检查指纹是否存在，如果是同一个来源，不算重复，指纹不存在则保存指纹）。

5. 递归搜索：\_execute\_deep\_search\(\)执行深度递归搜索，搜词 → 推结果 → LLM 分析 → 提取事实 → 若发现新线索且未超深度，则递归深挖，层层递进地追溯信息源头或追踪新线索。流程简述如下：

    1. 深度检查：先判断当前递归深度是否超过 `max_depth`（默认2层），超过则直接返回，防止无限递归。

    2. 遍历查询词：对传入的每个查询词，调用 `_execute_search` 执行搜索（每次取6条结果）。

    3. 实时推送结果：拿到结果后，立即通过 `add_message` 向前端推送增量搜索结果，并标记当前搜索类型（信源追溯/线索追踪）和递归深度。

    4. LLM 分析结果：调用 `_analyze_deep_search_results`，让 LLM 分析这批搜索结果，提取事实。

    5. 提取并添加事实：把 LLM 提取出的事实存入 `state`。

    6. 递归深挖（核心）：如果当前深度还没到上限，且 LLM 分析结果里发现了更深层的新线索（`further_tracing_queries`），就先发一条“发现更深层线索”的思考消息，然后带着新线索递归调用自身，深度加 1，直到达到 `max_depth` 为止。

    7. 信源追溯是文章说“据国家统计局数据”，就自动搜索"国家统计局 2024 汽车销量"；线索追踪是发现"特斯拉在华销量"，自动追踪"特斯拉 中国市场份额"

6. 网络搜索实现：\_execute\_search\(\)，使用Bocha API，支持搜索结果摘要，内存缓存避免重复搜索，异步执行

7. 本地知识库搜索：**\_execute\_local\_search\(\) \- Milvus 向量检索，**调用 `generate_embedding()` 生成查询向量，Milvus 向量相似度搜索，返回 Top\-K 结果（默认k=10）

8. 补充搜索：**\_supplementary\_research\(\)**

    1. 检查待办任务：从状态中取出审核阶段留下的 `pending_search_queries`（待补充的搜索问题列表）。

        - 如果没有需要补充的问题，直接跳过，进入写作阶段（WRITING）。

    2. 发送开始通知：如果有待补充的问题，先发一条思考消息，告知前端“根据审核反馈，开始补充搜索 N 个问题”。

    3. 循环执行补充搜索（最多 5 个）：

        - 每处理一个查询，先发一条 action 消息（告知用户正在使用 supplementary\_search 工具）。

        - 调用 `_execute_search` 执行网络搜索（每次取 8 条结果）。

        - 如果有结果，调用 `_analyze_supplementary_results` 让 LLM 分析提取新事实，并追加到全局 facts 列表中（补充之前缺失的信息）。

    4. 清理并推进阶段：处理完所有补充查询后，清空 `pending_search_queries` 列表，并把当前阶段切换为 WRITING（写作），准备进入最终报告生成环节。

    5. 总结是：查缺补漏 → 逐个补充搜索 → LLM 提取新事实 → 清空待办 → 推进到写作阶段

**\[深度阅读\]   deep\_read\_url\(\)深度阅读网页内容，抓网页 → 提正文 → 拼 Prompt 给 LLM → 返回结构化分析结果 ；\_extract\_text\_from\_html\(\)从HTML中提取纯文本正文，三级降级**

- trafilatura ：如果安装了 `trafilatura` 库，优先使用它来提取正文。配置了不包含评论、包含表格、偏向精确度等参数。如果提取出的文本长度超过 200 字符，说明质量合格，直接截断到 `max_length`（默认 12000）并返回。如果提取失败或内容过短，记录警告，降级到BeautifulSoup

- BeautifulSoup：用 `lxml` 解析 HTML。先移除无用标签（script、style、nav、header、footer、aside 等），减少噪音。然后尝试定位正文区域：按优先级遍历 `article`、`main`、`.content`、`.article`、`#content` 等常见选择器。如果找到了正文容器，就提取其中的文字；找不到就退而求其次，提取整个 `<body>` 的文字。提取后做空白清理（把连续 3 个以上换行合并为 2 个，把连续多个空格合并为 1 个），再截断返回。如果这一层也失败，降级到简单正则。

- 简单正则：为最后的兜底方案：不依赖任何第三方库，纯靠正则表达式。先用正则删掉 `<script>` 和 `<style>` 标签及其内容。再用正则删掉所有 HTML 标签（把 `<xxx>` 替换成空格）。然后解码常见的 HTML 实体（`&nbsp;`、`&lt;`、`&amp;` 等）。最后把连续空白压缩成单个空格，截断返回。

**\[知识图谱更新\]**   \_update\_knowledge\_graph\(\)，负责将新发现的实体（entities）以及它们之间的关系，动态地追加到全局知识图谱中，从state中取图谱 → 提取当前图谱中所有已存在节点的name建去重集合existing\_nodes → 遍历新实体（跳过重复）→ 加节点 → 加关系边 → 更新后的graph写回 state\["knowledge\_graph"\]。通过 `existing_nodes` 集合实现 O\(1\) 去重，保证知识图谱不会因为多次搜索而出现重复节点。

**\[假设验证\]    **\_update\_hypothesis\_status\(\)根据证据更新假设状态，取假设列表 → 逐条证据匹配 → 支持/反驳分类累加 → 满 2 条则改变状态 → 写回。这是一个简单的“证据计数阈值”机制：只有积累到至少 2 条一致方向的证据，才敢给假设下最终定论（支持或推翻），否则只能标记为“部分支持”，保持审慎。

**\[模型选择\]** qwen\-plus\(任务频繁，单次上下文长，不需要顶级推理，速度快\)，温度0\.2（确定性，搜索分析任务要忠于原文），max\_tokens=8000（“够用且不浪费”的输出额度，保证 JSON 完整、不被截断）

**\[SSE事件流\]**    research\_step（开始、完成搜索），action（Agent动作），search\_progress（搜索进度），search\_results（搜索结果），observation（观察结果），thought（思考过程）

## \[M02\-T04\] \[Agent \- DataAnalyst\]

**\[职责\]    **从文本（搜索结果）中提取结构化数据点、构建实体关系知识图谱（nodes \+ edges）、生成 ECharts 图表配置（JSON）【这里仅生成配置，不执行代码】、识别数据趋势和洞察

**\[Prompt设计\]  ：**DATA\_EXTRACTION\_PROMPT（从文本中提取结构化数据），KNOWLEDGE\_GRAPH\_PROMPT（构建知识图谱），CHART\_GENERATION\_PROMPT（生成ECharts图表配置）图表类型选择规则 ：时间序列数据 → `line` （折线图）；分类比较数据 → `bar` （柱状图）；占比分布数据 → `pie` （饼图）；进度/百分比 → `horizontal_bar` （横向进度条）；多维对比 → `radar` （雷达图）

**\[核心实现\]：**

1. process\(\) 入口

2. \_analyze\_data\(\) \- 数据分析流程：发开始事件 → 提数据 → 建图谱 → 生成图表 → 推图谱/图表事件 → 发完成事件

3. \_extract\_data\(\) \- 数据提取：取前 20 条事实格式化 → 拼 Prompt → LLM 提取 JSON → 数据点/洞察写回 state → 返回结果

4. \_build\_knowledge\_graph\(\) \- 知识图谱构建：取前 15 条事实（试出来的，太多了知识图谱输出太长太杂，效果反而不好）→ 拼 Prompt → LLM 提取实体和关系（nodes和edges） → 根据重要性（默认为5）算节点尺寸（根据公式 `size = 20 + importance * 3`计算出大小，最小23，最大50） → 返回图谱。

5. \_generate\_charts\(\) \- ECharts 图表生成：准备数据（从extracted\_data中去除三类数据：数据点，事件序列，分布，再加上state\["data\_points"\]中已有的前10条数据点作为补充） → 数据量校验，没数据就跳过 → LLM 生成 ECharts 配置 → 补全图标的唯一 ID → 返回图表列表

**\[模型选择\]：**qwen\-plus\(输入量大，调用频次高，难度中等\)，温度0\.2，max\_tokens=8000

**\[SSE事件流\]**    research\_step（开始、完成分析），knowledge\_graph（知识图谱），charts（图表配置）

## \[M02\-T05\] \[Agent \- CodeWizard\]

**\[职责\]   ** 唯一有权执行Python代码的Agent，负责数据清洗（统一不同来源的数据口径），统计分析\(计算关键指标（CAGR（年复合增长率）、同比等）\)，预测建模（简单的趋势预测），专业绘图（生成高质量数据可视化（PNG图片））

**\[Prompt设计\]  ： **

1. ANALYSIS\_PROMPT（生成数据分析代码）

    - 禁止使用反斜杠续行 ： `\` 导致 "unexpected character after line continuation character" 错误

    - 数据精简 ：只选取最关键的 5\-10 个数据点

    - 列字典格式 ： `data = {"Year": [2020, 2022], "Value": [100, 200]}`

    - 代码长度 ：不超过 40 行

    - 禁止 import ：已预导入 pd, np, plt, sns

    - 高级样式 ：seaborn 主题、专业配色、高 DPI

2. CHART\_PROMPT（生成特定类型图表的代码）：支持折线、柱状、饼图、散点图、热力图

3. CODE\_FIX\_PROMPT（修复执行失败的代码）

    - `could not convert string to float` → 使用 `pd.to_numeric()` 清洗数据

    - `SyntaxError` → 检查反斜杠、括号

    - `KeyError` → 检查列名

    - `TypeError` → 类型转换

**\[核心实现\]：**

1. process\(\) 入口：`phase == ANALYZING`或 `data_points >= 3`才进入分析 → 调用 `_analyze_data` 做全套分析 → 图表生成→ 返回状态。

2. \_analyze\_data\(\) \- 数据分析：取数据点，格式化 → 拼接Prompt，LLM 生成分析代码 → 清理代码 → 执行（出错自愈）→ 收集图表并逐个推送。

3. \_execute\_in\_sandbox\(\) \- 安全沙箱：建白名单 → 禁危险函数 → 设中文字体 → 执行代码 → 抓 stdout/stderr（把代码执行过程中的标准输出和错误输出重定向到内存缓冲区，避免污染主程序的日志） → 捕获生成的图表，转 base64字符串，放进charts列表，然后关闭凸形释放内存 → 返回结果。

    1. **白名单 import **：只允许 pandas, numpy, matplotlib, seaborn 等安全模块

    2. **禁用危险函数 **：禁用 `open` , `exec` , `eval` , `os` , `sys` , `subprocess`

    3. **禁止网络访问 **：禁用 `requests` , `urllib` , `socket`

    4. **非交互式后端 **： `matplotlib.use('Agg')` ，不弹窗

    5. **中文字体预设 **：避免中文乱码

4. \_execute\_with\_self\_correction\(\) \- 带自愈的执行：循环执行代码（最多重试 3 次） → 成功就返回（包含输出、图表、重试次数和最终代码的结果字典） → 失败，取出error和stdout，就让 LLM 分析错误并修复 → 修复后再执行，若循环结束仍未成功返回失败。

5. \_clean\_code\(\) \- 清理 LLM 输出：用于修复LLM生成代码中的格式问题，LLM可能输出：反斜杠续行；转义的 \\n；LaTeX 风格换行；语句粘连。对此清理策略为：去 Markdown 代码块标记→ 正常代码直接逐行 `rstrip` 去尾空格并返回 → 定义占位符保护字符串内 `\n` → 替换各种假换行为真换行 → 修复语句粘连（用正则匹配“前一句的结尾符号（`]`、`)`、`"`、`True`、`False`、`None`）”后面紧跟“下一句的开头（`plt.`、`fig =`、`ax.`、`df =`）”的情况，在中间插入换行符。） → 从多到少处理多重转义的 `\n` → 恢复占位符保护的正常`\n` → 移除 import/rcParams/续行符 → 返回。

6. \_save\_debug\_log\(\) \- 单步调试：首次调用建时间戳目录 → 每个步骤写一个独立文件 → 记录时间/长度/内容。

**\[模型选择\]：**deepseekv3\.2，温度0\.3，max\_tokens=4000

**\[SSE事件流\]**    code（生成的代码），code\_result（执行结果），code\_fix（自愈修复），chart（生成的图表）

**\[安全限制\]**    黑名单拦截危险操作（删文件、执行命令、联网），白名单放行安全模块（数据分析、绘图、文本处理）。

## \[M02\-T06\] \[Agent \- LeadWriter\]

**\[职责\]   ** 深度写作（撰写有逻辑、有深度的行业分析），Markdown 排版（专业的格式规范），图文混排（整合文字、图表、数据），参考文献（规范的引用格式），两种模式（初稿撰写 vs 审核后修订）

**\[Prompt设计\]  ： **

1. SECTION\_WRITING\_PROMPT（单个章节撰写）

    - 专业性：使用行业术语

    - 逻辑性：论点清晰，论据充分

    - 数据支撑：关键观点必须有数据或事实支撑

    - 引用规范： `[来源名称](URL)` 格式

    - 图表整合： `![图表标题](chart_id)` 占位符

    - 字数控制：500\-1000 字

    - 不重复标题：正文开头不要再写章节标题

2. SYNTHESIS\_PROMPT（整合各章节成完整报告）：撰写报告摘要（Executive Summary），整合各章节，确保逻辑连贯，撰写结论与展望，整理参考文献列表

    - 标题编号规则：1、1\.1、1\.1\.1（不要在正文中重复标题）

    - 引用格式： `[来源名称](URL)` （确保可点击）

    - 报告结构：不使用 `#` 一级标题，直接从"执行摘要"开始

3. REVISION\_PROMPT（根据审核反馈修订报告）

    1. 针对性修改：只修改有问题的部分

    2. 补充来源：对缺少来源的观点补充引用

    3. 修正错误：纠正事实错误或逻辑漏洞

    4. 保持风格：修订后保持报告整体风格一致

**\[核心实现\]：**

1. process\(\) 入口：看阶段 → 是写作就写报告 → 是修订就改报告 → 都不是就跳过

2. \_write\_report\(\) \- 撰写报告：发开始事件 → 逐章节写（跳过已写的）→ 整合完整报告 → 发完成事件 → 切到审核阶段

3. \_write\_section\(\) \- 撰写单个章节：收集事实/数据/图表 \+ 前五条insights→ 拼 Prompt ，调用LLM，temperature=0\.4（允许行文又文采），max\_tokens=16000→ LLM 生成章节内容 → 存草稿 \+ 收集引用 → 推送前端展示。

4. \_synthesize\_report\(\) \- 整合报告：发通知 → 收集章节和来源（合并已收集的参考文献，事实里的来源，并做去重检查，最终最多取前30条来源） → LLM 整合润色 → 成功则存最终报告/失败则手动拼接 → 推送完成事件。

5. \_revise\_report\(\) \- 修订报告：收集未解决问题\(从 `state["critic_feedback"]` 中筛出 `resolved` 为 `False` 的问题，格式化成 `- [严重程度] 问题描述 + 建议`\) \+ 新信息\(取 state\["facts"\] 中最后 5 条（通常是补充搜索新增的事实），每条截取前 200 字符，防止太长。\) → LLM 修订报告\(原报告内容截取前6000字符与反馈列表\+新信息填入Prompt模板，temperature=0\.3，max\_tokens=16000\) → LLM返回`revised_content`（修订后的报告）、`addressed_issues`（已解决的问题 ID 列表）、`changes_made`（修改点）、`unable_to_address`（无法解决的问题）→ 更新报告 \+ 标记已解决问题 → 切回审核阶段。

**\[初稿模式与修订模式对比\]**

|特性|初稿模式|修订模式|
|---|---|---|
|触发阶段|WRITING|REVISING|
|输入|事实、数据、大纲|原报告 \+ 审核反馈 \+ 新信息|
|处理流程|逐章节撰写 → 整合|直接修订全文|
|temperature|0\.4（更有创造性）|0\.3（更保守）|
|输出|完整报告草稿|修订后的报告|
|更新状态|draft\_sections \+ final\_report|只更新 final\_report|

**\[模型选择\]：**deepseek v3\.2，温度0\.4（初稿），max\_tokens=16000

**\[SSE事件流\] **    research\_step（开始/完成写作），thought（思考过程），action（Agent 动作），section\_content（章节内容），report\_draft（报告草稿），revision\_complete（修订完成）。

**\[引用规范化\]     **

1. 收集引用来源：从两个地方汇总参考文献。一是从各章节写作结果里提取 LLM 返回的 `citations`，存入 `state["references"]` 并自动编号；二是从事实库（`facts`）里补充来源，做去重后加入 `all_sources` 列表。

2. 生成参考文献：定义标准化的引用数据结构（JSON 格式），包含 `id`、`title`、`url`、`author`、`date` 等字段，确保每条引用都有完整的元信息。

3. 前端渲染：把结构化的引用数据转换成 Markdown 格式（如 `1. [标题](链接) - 作者, 日期`），供前端展示。

## \[M02\-T07\] \[Agent \- CriticMaster\]

**\[职责\]   ** 

1. **对抗式质检 **：假设一切都有问题

2. **逻辑漏洞检测 **：检查推理链条是否严密

3. **幻觉查杀 **：识别无来源或错误的信息

4. **偏见识别 **：发现观点偏颇或情绪化表达

5. **智能路由 **：决定下一步是补充搜索还是仅修改文字

6. **质量评分 **：给出客观的质量评分（1\-10分）

**\[Prompt设计\]  ： **

1. REVIEW\_PROMPT（审核报告草稿）:critical、major、minor，评分1\-10（\>=7 pass）

    1. **零容忍幻觉 **：任何没有明确来源的数据或事实，都是问题

    2. **逻辑闭环 **：论点必须有论据支撑，论据必须有来源

    3. **偏见警惕 **：单方面观点、情绪化表达都是问题

    4. **时效性 **：过时的数据（超过2年）必须标注

    5. **完整性 **：是否遗漏重要方面

2. FINAL\_CHECK\_PROMPT（修订后再次审核，最终质量把关）

    - 检查之前的问题是否已解决

    - 是否有新问题产生

    - 给出最终评语

**\[核心实现\]  ： **

1. process\(\) 入口：阶段是REVIEWING，发送开始通知，\_review\_content\(state\)审核报告 → 返回审核结果（问题列表，总体评估等） →  遍历审核发现的问题，为问题生成唯一ID标记resolved=False，追加到state\["critic\_feedback"\] ,更新 `state["quality_score"]`（质量分数）和 `state["unresolved_issues"]`（未解决的严重问题数）。推送 `review` 事件，包含：审核结论、质量分、问题总数、严重/重要问题数、摘要、缺失的方面。  → 根据结论智能路由:

    - `pass`（通过）：直接进入 `COMPLETED`（完成阶段）。

    - 达到最大迭代次数：强制进入 `COMPLETED`，并推送警告“部分问题可能未解决”。

    - 否则（需要修改）：调用 `_analyze_issues_for_routing` 判断问题类型：

        - 需要补充搜索（信息缺失）：切到 `RE_RESEARCHING` 阶段，并把待搜索问题写入 `state["pending_search_queries"]`。

        - 只需文字修改：切到 `REVISING` 阶段。

        - 最后 `state["iteration"] += 1`，累计迭代次数。

2. \_analyze\_issues\_for\_routing\(\) \- 智能路由：从审核结果中取出issue问题列表和missing\_aspects缺失的方面，看问题类型（缺来源/不完整/过时）\+ 看严重程度（critical/major需要\+1）→ 如果问题明确要求重新搜索（`requires_new_search`）并提供了搜索词（`search_query`），就把搜索词加入 `search_queries`。→ 补充遗漏方面的搜索词，遍历 `missing_aspects` 的前 3 条，把它们也作为搜索词加入。→ 满足以下所有条件时，需要补充搜索：有搜索词（`len(search_queries) > 0`）；有需要搜索的严重问题，或有遗漏的方面；要么没有严重问题，要么“需要搜索的严重问题”占比超过 30%。→最后返回 `{"should_research": bool, "search_queries": [去重后的最多5个查询]}`。

3. \_review\_content\(\) \- 执行审核：遍历 `state["draft_sections"]`草稿/取 `state["facts"]` 前 20 条事实（格式化为\- \[ID\] 内容前150字（来源，可信度））/取 `state["data_points"]` 前 15 条数据（格式化为\- 名称：值 单位（来源））/遍历 `state["outline"]`大纲 （格式化成 `- ID: 标题 (状态)`）→ 拼 Prompt（草稿截取8000字符）→ 用“严苛审核员”人格调 LLM → 解析 JSON 返回。

**\[6类问题类型\]     **missing\_source（缺少来源），logic\_error（逻辑错误），bias（偏见），hallucination（幻觉），outdated（过时），incomplete（不完整）

**\[质量评分机制\]     **quality\_score = 来源完整性 \* 0\.3 \+ 逻辑严密性 \* 0\.3 \+ 客观中立性 \* 0\.2 \+ 时效性 \* 0\.1 \+ 完整性 \* 0\.1

**\[决策逻辑\]**

1. \_should\_revise 函数：`unresolved_issues > 0`  **且 **`iteration < max_iterations` → `"revise"`

2. SSE事件流：thought（思考过程），review（审核结果），critic\_feedback（具体问题 critical 级别），warning（警告信息）。

3. 迭代控制：最大迭代词数为3次，达到最大迭代次数强制完成并输出warning

4. 审核流程：评分 → 分数大于等于7可以Completed → 分数不过关，判断轮次，大于等于最大迭代轮次强制completed → 未达到最大轮次分析问题类型 → 判断是否要补充检索 → 补充检索/仅修订 → 回到审核阶段

## \[M02\-T09\] \[记忆层实现\]

**\[记忆层架构\]  **

1. 用户对话

2. 短期记忆层（实时对话）：当前会话消息列表（ChatMessage），当前Token统计，触发阈值10,000 tokens，如果超过阈值触发压缩

3. 记忆压缩引擎：LLM总结（Qwen\-Plus），输入对话历史，输出结构化summary，key\_insights，user\_preference，topics，压缩率为95%

4. 长期记忆层（永久存储）：分为两部分，如果新对话需要上下文，就混合检索召回（Top\-3），构建增强上下文，传递给LLM。

    1. PostgreSQL存储：原始文本，靠SQL精确匹配查询，数据完整，可靠，只能字面匹配

    2. Milvus向量存储：存向量，向量相似度搜索，能理解语义，没有SQL精确

**\[核心概念\]     **

|特性|短期记忆（Working Memory）|长期记忆（Long\-term Memory）|
|---|---|---|
|存储位置|内存/当前会话|PostgreSQL \+ Milvus|
|生命周期|当前会话|永久（除非用户删除）|
|容量限制|受上下文窗口限制|理论无限|
|访问方式|直接传递给LLM|向量检索召回|
|内容|完整对话历史|总结、洞察、偏好|

记忆压缩可以主动触发（用户点击“保存为记忆”按钮），自动触发（会话token超阈值），定期触发（30min一次检查活跃会话）

**记忆数据模型**

```Python
class LongTermMemory(Base):
    """长期记忆模型"""
    __tablename__ = "long_term_memories"

    id = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)

    # 关联信息
    user_id = Column(UUID(as_uuid=True), ForeignKey("users.id", ondelete="CASCADE"))
    session_id = Column(UUID(as_uuid=True), ForeignKey("chat_sessions.id", ondelete="SET NULL"), nullable=True)

    # 记忆内容
    summary = Column(Text, nullable=False)  # 对话摘要
    key_insights = Column(JSONB)            # 关键洞察（结构化数据）
    # {
    #   "summary": "...",
    #   "key_insights": ["洞察1", "洞察2"],
    #   "user_preferences": {...},
    #   "topics": ["主题1", "主题2"]
    # }

    # 向量索引
    milvus_ids = Column(ARRAY(Text))  # Milvus中的向量ID列表

    # 元数据
    token_count = Column(Integer)     # 压缩前的Token数
    created_at = Column(DateTime, default=datetime.utcnow)

    # 关系
    user = relationship("User", back_populates="memories")
    session = relationship("ChatSession", back_populates="memories")
```

**\[核心实现\]**

1. 记忆总结（LLM压缩）：构建对话文本→限制长度→调用LLM总结（使用Prompt）→清理Markdown标记→解析JSON→返回默认结构（单次压缩成本是0\.05元）

2. 记忆向量化存储：定义Schema→创建COSINE相似度索引→存储摘要向量→存储关键洞察向量（每个洞察独立向量化）→ 存储主题向量 → 批量插入Milvus

    1. 向量化策略：摘要整体向量化（用于召回整个对话摘要），每条洞察独立向量化（精细粒度检索），主题列表组合向量化（主题匹配）

    2. 为什么分开向量化：提高检索精度（可以匹配到具体洞察），支持多粒度召回（整体摘要\+具体细节），灵活的相关性计算。

3. 记忆检索与召回：class MemoryService，def retrieve\_memorise\(\)，检查集合（长期记忆）是否存在 → 生成查询向量 → 按用户过滤（只检索当前用户的记忆）→ 配置搜索参数（余弦相似度，探测10个聚类）→ 执行向量检索 → 格式化结果
