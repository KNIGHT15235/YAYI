# \[P00\] 项目总览

一句话介绍：01-YAYI 的行业信息助手原型，使用六个专业 Agent 完成问题规划、网络/知识库检索、数据分析、报告生成与审核修订。可用于通用资料调研；尚未建设科研文献专用数据库、论文管理和模型训练流水线。

特点：6个Agent分工协作，假设驱动研究、信源追溯、实时SSE、检查点恢复

**[P00-Q01] [为什么使用 AI Agent 系统？]** 当前实现包括内外部资料检索、分阶段规划与执行、Text2SQL、图表生成以及长期记忆。Fine-tuning、微服务拆分、大规模水平扩展和7×24服务等级属于后续规划；使用Docker、Redis和异步代码本身不能证明这些目标已经达成。

核心类为 `DeepResearchGraph`。下面展示的是保留的StateGraph构图示意，不是当前生产入口的可直接切换配置；主入口使用 `_run_simplified` 和异步队列执行。文档中的省略代码仅说明结构。

```Python
class DeepResearchGraph:
    def __init__(self, llm_api_key, llm_base_url, search_api_key, model):
        *# 初始化6个Agent*
        self.architect = ChiefArchitect(...)
        self.scout = DeepScout(...)
        self.data_analyst = DataAnalyst(...)
        self.wizard = CodeWizard(...)
        self.critic = CriticMaster(...)
        self.writer = LeadWriter(...)

        *# 构建LangGraph状态图*
        self.graph = self._build_langgraph()

    def _build_langgraph(self):
        workflow = StateGraph(ResearchState)

        *# 添加节点*
        workflow.add_node("plan", self._plan_node)
        workflow.add_node("research", self._research_node)
        workflow.add_node("analyze", self._analyze_node)
        workflow.add_node("write", self._write_node)
        workflow.add_node("review", self._review_node)
        workflow.add_node("revise", self._revise_node)

        *# 设置边和条件路由*
        workflow.add_edge("plan", "research")
        workflow.add_edge("research", "analyze")
        workflow.add_conditional_edges(
            "review",
            self._should_revise,
            {"revise": "revise", "complete": END}
        )

        return workflow.compile()
```

**\[状态管理\]**

  → REVIEWING → \(RE\_RESEARCHING / REVISING\) → COMPLETED

每个阶段结束后，状态会被序列化保存到检查点服务

**\[数据存储层\]**

- PostgreSQL数据库：研究页面左侧的tab信息储存格式以结构化形式存储

- Milvus向量数据库

    - 向量化流程：文档上传→文档解析→文本分块→调用阿里text\-embedding\-v4生成1024维向量→插入Milvus \+ PostgreSQL元数据

- Redis缓存

    - 研究检查点存储在PostgreSQL JSONB，记录下一执行阶段、最终报告和UI状态；没有24小时自动过期策略。Redis用于取消标记、运行租约、请求频率及缓存。

    - Redis保存5分钟取消标记；运行租约有效期120秒，每30秒续期。完整研究状态仍在PostgreSQL检查点中。

    - Bocha检索缓存使用Redis，默认TTL为15分钟；键包含查询文本、结果数量与时效参数。缓存不可用时直接请求搜索服务。

**\[知识库查询数据流\]**

用户输入查询问题

→ Frontend：选择知识库\+输入问题

→ API：POST /knowledge-bases/{kb_id}/search，先验证当前用户归属和历史名称集合冲突

→ Embedding Service：阿里text\-embedding\-v4，生成query向量（1024维）

→ Milvus：默认取Top-10余弦相似度候选，top_k可设1—50，返回正文、相似度和切片信息

→ DashScope Rerank：对候选重新排序，原始余弦分数和重排分数分别保留；重排服务不可用时保留向量排序并返回提示。这里描述的是实际调用的服务，不推断服务内部模型架构。

→ Frontend：展示段落、安全高亮查询词、相似度评分和原文件下载。原文件下载需要当前用户鉴权；新上传文件保留在backend/storage/knowledge，旧版本已删除的原件无法恢复，需重新上传。

**\[Text2SQL数据流\]**

用户输入自然语言问题

→ Frontend: 输入 "2024年XX行业营收前三名"

→ API：POST /database/text2sql

→ Text2SQLService：动态读取company_data、industry_stats、policy_data实际列和主键，不把用户账号及记忆表结构发送给模型

→ LLM：当前路由使用qwen-plus，生成SQL、解释和visualization_hint

→ SQL Validator（检查SQL安全性，禁止drop和delete，限制查询结果数量100条）

→ PostgreSQL执行查询返回结果集

→ 结果展示：返回表格；前端根据visualization_hint与实际列类型生成柱状、折线、饼图等适用图表。空数据或不适合绘图时保留表格，不虚构数值。

**\[性能优化\]**

- 并发处理

    1\. 并行搜索 : DeepScout对多个章节并发执行搜索

    2\. 异步LLM调用 : 使用\`asyncio\`并发调用多个LLM接口

    3\. 流式输出 : 边计算边推送，减少用户等待时间

- 缓存策略

    1. 搜索结果缓存：Redis，默认15分钟，包含搜索参数。

    2. 向量缓存：相同文本在相同账号、接口、模型、维度、编码配置下复用向量，默认24小时；同批重复文本只请求一次。EMBEDDING_CACHE_TTL_SECONDS=0可关闭。它减少重复向量调用，不等于文件永久不再计算。

    3. 研究LLM响应缓存：仅成功的非流式响应，默认1小时；键包含用户范围、账号摘要、模型、消息及请求参数。缓存不可用时降级为正常请求。

    质量审核Critic绕过响应缓存；HTTP成功不代表五维评分已通过业务校验，审核及纠正请求均重新调用模型。

- 数据库优化

    1\. 索引优化 : 在高频查询字段建立索引

    2\. 分页查询 : 限制单次查询结果数量

    3\. 连接池 : 复用数据库连接

**\[安全机制\]**

- 认证鉴权

    JWT Bearer Token：验证签名与有效期，并从PostgreSQL确认用户；客户端当前使用localStorage。

    Password Hashing：bcrypt密码哈希存储，不存储明文密码。

    CORS配置 : 限制跨域请求

- 输入验证

    Pydantic Schema : 自动验证请求参数

    SQL执行：参数化应用查询；用户/模型SQL经单条SELECT验证、结果数量限制及PostgreSQL只读事务。此机制没有实现数据库表/行级租户权限。

    XSS防护 : Markdown渲染时过滤危险标签

- 速率限制

    研究限流：按已认证用户统计启动/恢复请求，每60秒最多10次；每用户同时最多一个研究，同一会话禁止重复执行。运行冲突返回409或429，协调服务不可用时返回503。

    文件上传：知识库单文件最大100MB；聊天附件最大100MB，图片最大20MB。文件名不参与服务端实际存储路径。

# \[M01\] \[技术选型\]

性价比，实用，可控，可扩展。

**[M01-Q01] [为何保留LangGraph构图？]** 下表是框架评估。当前生产路径采用asyncio.Queue，以支持逐条SSE和既有检查点恢复；LangGraph构图保留为实验代码。

|**框架**|**优势**|**劣势**|
|---|---|---|
|LangGraph|状态机透明可控，灵活路由，状态持久化，流式输出|需要手动构建图,学习曲线稍陡|
|CrewAI|上手简单,Agent定义直观|黑盒较多,难以调试复杂流程|
|AutoGen|微软出品,与Azure集成好|文档较少,社区小|

**[M01-Q02] [为何混合使用DeepSeek和Qwen？]** 默认以deepseek-v3.2承担规划、数据分析、代码和写作，DeepScout与质量审核Critic使用qwen-plus。审核模型可通过CRITIC_MODEL独立配置；其切换不改变五维量表、加权公式和通过门槛。模型选择是工程配置，不保证固定质量或速度；费用以实际配置与服务商账单为准。

**[M01-Q03] [为何选择Milvus？]** 用于自部署向量检索，当前以1024维向量和COSINE度量存储知识库与记忆。未进行百万向量规模或GPU检索压测，不能给出小于100ms的项目性能保证。

**\[M01\-Q04\]\[为什么选择FastAPI\]     **LLM调用，搜索API，数据库查询都是IO密集型，异步可以显著提升性能，Swagger UI开箱即用，方便前后端联调，Pydantic自动验证参数格式，原生支持流式响应

**[M01-Q05] [为何选择ECharts？]** 通过配置生成常用图表，前端负责展示与尺寸适配；具体图表效果取决于数据、配置和浏览器环境。

**\[M01\-Q06\]\[为什么选择多智能体\]   **单智能体Prompt过长，超出上下文窗口，LLM容易遗漏细节，难以质量把控，无法并行处理，出错后全部重来。多智能体课可以拆解任务，6个专业Agent分工，每个Agent Prompt简洁，效果更好，可以针对性选择模型，出错后只需重试特定Agent，支持并行处理，容易扩展新功能。

**[M01-Q07] [为何使用检查点？]** 每个阶段保存状态、UI和下一阶段。中断后可手动继续最近检查点；尚未完成阶段可能重新执行，已经提交的外部同步请求不一定能被强制终止。因此不能保证所有中途token与外部调用均可回收。

**[M01-Q08] [为何采用SSE？]** 研究主要需要服务端持续推送进度。前端通过带Bearer Token的fetch读取SSE流，后端持续yield事件并发送心跳。恢复由检查点和手动继续按钮完成；不等同于EventSource自动重连。

**[M01-Q09] [为何由CodeWizard执行代码？]** 将代码生成与绘图集中到一个Agent，便于限制模块、检测危险模式、错误重试和收集图表。当前执行器使用同进程exec，独立全局字典不构成安全沙箱；pandas/numpy等模块仍可能间接访问文件。不能声称无法访问真实文件系统或只能生成图表，生产部署需另建进程/容器隔离与资源配额。

**\[M01\-Q10\]\[为什么采用假设驱动研究\]   **传统关键词搜索研究方向不明确，易遗漏关键问题，信息碎片化，缺乏逻辑。假设驱动研究有明确方向，信息收集更有针对性，报告逻辑更严密 \(假设\-验证\-结论， 支持动态调整研究路径

**[M01-Q11] [为何采用PostgreSQL？]** 保存账号、会话、文档元数据、记忆摘要和JSONB检查点，支持事务、索引和关系查询。当前关键词筛选使用SQL文本匹配；未配置专门中文全文分词，也没有启用pg_vector作为本项目向量检索路径。

**\[M01\-Q12\]\[为什么向量数据库和关系数据库分离\]**

```text
Milvus：保存向量、切片正文、文件名等检索字段；当前知识库索引为IVF_FLAT/COSINE，nlist=128，nprobe=10。
PostgreSQL：保存用户、会话、文档详情、记忆和检查点。
知识库搜索接口：验证用户 → 向量检索/重排 → 按该知识库的文档元数据补充下载信息。
```

历史知识库集合按名称归一化，并非完整的tenant_id物理隔离。冲突集合会拒绝用户检索和变更；没有静默迁移、合并或删除历史向量。不同向量数据库之间的性能优劣需在同一数据集和配置下实测。

**[M01-Q13] [JWT认证如何实现？]** 登录后前端在localStorage保存Token，请求携带Authorization: Bearer。后端验证Token后查询PostgreSQL用户，因此不是“每次无需访问数据库”。Markdown经过DOMPurify过滤。当前未迁移HttpOnly Cookie，也未部署完整CSP策略，不能把两者描述为现有措施；迁移需要同时设计CSRF、跨域和会话兼容策略。

**[M01-Q15] [为什么使用异步？]** asyncio适合并发等待网络IO，但不会自动把同步SDK或CPU计算变成非阻塞任务。项目部分同步操作通过线程池执行。常见CPython中，纯Python CPU密集任务会受GIL限制；IO操作和部分数值库可释放GIL。需要CPU并行或强隔离时应评估多进程，而非声称异步没有性能瓶颈。

**[M01-Q16] [为何缓存搜索结果？]** 使用查询文本、数量和时效参数构造哈希键，在Redis缓存15分钟；相同参数可复用结果，过期后重新查询。缓存故障不阻止搜索请求。哈希碰撞概率很低，但不是数学意义上的不可能。

**[M01-Q17] [如何扩展Agent？]** 继承Agent基类，实现process方法，定义状态与事件，再将调用接入当前asyncio主流程并补充检查点、取消和前端事件处理测试；只注册StateGraph节点不会自动改变当前生产路径。

**\[M01\-Q18\]\[如何扩展新的数据源\]   **在DeepScout中新增方法，这个方法负责去调用外部API，然后把返回的数据格式化为统一的内部结构，在主流程中按条件合并，if判断是否启动这个数据源，后续逻辑不变

**\[M01\-Q19\]\[如何支持新的图表类型\]  **加个 Prompt 模板 → 写个新方法（拼 Prompt → 调 LLM → 执行代码）。通过“新增模板\+新增方法”实现图表类型的即插即用，底层执行逻辑完全复用。

**[M01-Q20] [LangGraph与当前编排的关系？]** LangGraph用于保留的状态图实验；生产入口由asyncio阶段流程负责。采用哪个框架需要以实时事件、恢复一致性和测试结果决定，当前没有可直接切换的双引擎配置。

**\[M01\-Q21\]\[为什么不全用开源LLM \(如Llama\)?\]   **开源LLM部署成本高\(需GPU服务器\),维护复杂\(模型更新、优化\)。闭源API按需付费,更灵活,且Deepseek性价比已经很高。

**[M01-Q22] [能否离线部署？]** 当前版本仍调用云端LLM、Embedding、Rerank、DocMind和网络搜索，不能直接离线运行。离线部署需要替换这些服务、准备本地模型/数据及重新验收。

**[M01-Q23] [多用户并发性能如何？]** 本次仅有功能和少量并发控制测试，未测量200—300并发研究。容量数据需通过代表性模型、文档规模和机器配置的压测产生。

## \[M02\-T03\] \[Agent \- DeepScout\*\*\*\]

**[职责]** 网络与本地知识库搜索、受预算约束的网页原文阅读、递归线索追踪、模型信源评级、数字/中文片段哈希启发式去重、假设证据累计、知识图谱与补充搜索。评级、指纹和证据计数都不构成独立事实核验。

**\[Prompt设计\]  ：**SEARCH\_ANALYSIS\_PROMPT（角色，输入定义，任务，输出，fewshot/特殊标准/特殊说明，用于分析搜索结果并提取结构化信息）；DEEP\_READ\_PROMPT（用于深度阅读长文本，网页正文，提取文档摘要、关键事实、数据表格、重要原文引用）；补充搜索分析 Prompt（用于分析补充搜索结果（CriticMaster 审核后发现信息缺失时使用））；深度搜索分析 Prompt（用于分析递归搜索的结果（信源追溯或线索追踪））

**\[核心实现\]：**

1. process\(\)入口：首先路由判断（正常研究\+补充搜索双模式路由）；然后是准备工作，尝试获取股票数据，更新状态为“研究中”，读取搜索配置（网络/本地），筛选出所有pending章节；向系统发送出一条“信息检索开始”的通知，附带进度统计；asyncio\.gather\(\)多章节并行搜索，从pending章节中每次最多取3个；发送完成事件，所有搜索任务跑完后，发送“检索完成”的通知，并统计结果数量和来源数量，最后触发搜索结果事件并返回状态，配合SSE实时事件流。

2. asyncio\.gather\(\)实现：首先准备配置，从章节中获取搜索词列表，并读取当前是本地搜索还是网络搜索；逐词搜索，若开启网络搜索，调用 `_execute_search` 拿结果，立刻通过 `add_message` 向前端推送当前进度和增量搜索结果（供 UI 实时展示），若开启本地搜索，同样调用本地检索并推送；把所有搜索结果交给 `_analyze_search_results` 进行大模型分析（提取事实、验证假设）；遍历 LLM 返回的`extracted_facts`，进行去重检查，将新事实和关联的数据点写入 `state["facts"]` 和 `state["data_points"]`；如果未达迭代上限可以递归深挖，信源追溯（最高优先级）：如果分析结果里有 `source_tracing_queries`，调用 `_execute_deep_search` 去追溯原始信源。线索追踪：如果分析结果里有 `follow_up_queries`，同样调用 `_execute_deep_search` 去追踪新发现的线索。每个 `_research_section()`  是一个独立的协程，同时执行，提升效率。

3. 信源可信度评级算法：评分标准在prompt中预设，官方来源0\.9\-1\.0，学术来源0\.8\-0\.95，权威媒体0\.7\-0\.85，行业报告0\.7\-0\.9，一般新闻0\.5\-0\.7，自媒体0\.2\-0\.5，LLM 根据 `source_name` 和 `source_url` 判断类型，输出 `credibility_score`自动评分

4. 事实去重：`_compute_fact_fingerprint()`提取数字和中文片段并计算哈希，`_is_duplicate_fact()`结合来源判断重复；这是启发式文本去重，不是语义向量匹配，也不能证明不同来源的事实互相独立或真实。

5. 递归搜索：\_execute\_deep\_search\(\)执行深度递归搜索，搜词 → 推结果 → LLM 分析 → 提取事实 → 若发现新线索且未超深度，则递归深挖，层层递进地追溯信息源头或追踪新线索。流程简述如下：

    1. 深度检查：先判断当前递归深度是否超过 `max_depth`（默认2层），超过则直接返回，防止无限递归。

    2. 遍历查询词：对传入的每个查询词，调用 `_execute_search` 执行搜索（每次取6条结果）。

    3. 实时推送结果：拿到结果后，立即通过 `add_message` 向前端推送增量搜索结果，并标记当前搜索类型（信源追溯/线索追踪）和递归深度。

    4. LLM 分析结果：调用 `_analyze_deep_search_results`，让 LLM 分析这批搜索结果，提取事实。

    5. 提取并添加事实：把 LLM 提取出的事实存入 `state`。

    6. 递归深挖（核心）：如果当前深度还没到上限，且 LLM 分析结果里发现了更深层的新线索（`further_tracing_queries`），就先发一条“发现更深层线索”的思考消息，然后带着新线索递归调用自身，深度加 1，直到达到 `max_depth` 为止。

    7. 信源追溯是文章说“据国家统计局数据”，就自动搜索"国家统计局 2024 汽车销量"；线索追踪是发现"特斯拉在华销量"，自动追踪"特斯拉 中国市场份额"

6. 网络搜索实现：`_execute_search()`调用Bocha API；Redis缓存900秒，键包含query、count、freshness，缓存不可用时直接搜索，调用通过异步流程执行。

7. 本地知识库搜索：**\_execute\_local\_search\(\) \- Milvus 向量检索，**调用 `generate_embedding()` 生成查询向量，Milvus 向量相似度搜索，返回 Top\-K 结果（默认k=10）

8. 补充搜索：**\_supplementary\_research\(\)**

    1. 检查待办任务：从状态中取出审核阶段留下的 `pending_search_queries`（待补充的搜索问题列表）。

        - 如果没有需要补充的问题，直接跳过，进入写作阶段（WRITING）。

    2. 发送开始通知：如果有待补充的问题，先发一条思考消息，告知前端“根据审核反馈，开始补充搜索 N 个问题”。

    3. 循环执行补充搜索（最多 5 个）：

        - 每处理一个查询，先发一条 action 消息（告知用户正在使用 supplementary\_search 工具）。

        - 调用 `_execute_search` 执行网络搜索（每次取 8 条结果）。

        - 如果有结果，调用 `_analyze_supplementary_results` 让 LLM 分析提取新事实，并追加到全局 facts 列表中（补充之前缺失的信息）。

    4. 清理并推进阶段：处理完所有补充查询后，清空 `pending_search_queries` 列表，并把当前阶段切换为 WRITING（写作），准备进入最终报告生成环节。

    5. 总结是：查缺补漏 → 逐个补充搜索 → LLM 提取新事实 → 清空待办 → 推进到写作阶段

**[深度阅读]** 主流程在网络搜索后、分析前调用`deep_read_url()`。每次研究最多深读3个去重URL；仅允许公网HTTP(S)及80/443端口，校验DNS和每次重定向并固定连接IP。单页响应最多1MB，抓取约10秒、等待约12秒、含模型分析整体预算25秒，最多3次重定向。失败时保留搜索摘要继续。正文依下述三层方式提取。

- trafilatura ：如果安装了 `trafilatura` 库，优先使用它来提取正文。配置了不包含评论、包含表格、偏向精确度等参数。如果提取出的文本长度超过 200 字符，说明质量合格，直接截断到 `max_length`（默认 12000）并返回。如果提取失败或内容过短，记录警告，降级到BeautifulSoup

- BeautifulSoup：用 `lxml` 解析 HTML。先移除无用标签（script、style、nav、header、footer、aside 等），减少噪音。然后尝试定位正文区域：按优先级遍历 `article`、`main`、`.content`、`.article`、`#content` 等常见选择器。如果找到了正文容器，就提取其中的文字；找不到就退而求其次，提取整个 `<body>` 的文字。提取后做空白清理（把连续 3 个以上换行合并为 2 个，把连续多个空格合并为 1 个），再截断返回。如果这一层也失败，降级到简单正则。

- 简单正则：为最后的兜底方案：不依赖任何第三方库，纯靠正则表达式。先用正则删掉 `<script>` 和 `<style>` 标签及其内容。再用正则删掉所有 HTML 标签（把 `<xxx>` 替换成空格）。然后解码常见的 HTML 实体（`&nbsp;`、`&lt;`、`&amp;` 等）。最后把连续空白压缩成单个空格，截断返回。

**\[知识图谱更新\]**   \_update\_knowledge\_graph\(\)，负责将新发现的实体（entities）以及它们之间的关系，动态地追加到全局知识图谱中，从state中取图谱 → 提取当前图谱中所有已存在节点的name建去重集合existing\_nodes → 遍历新实体（跳过重复）→ 加节点 → 加关系边 → 更新后的graph写回 state\["knowledge\_graph"\]。通过 `existing_nodes` 集合实现 O\(1\) 去重，保证知识图谱不会因为多次搜索而出现重复节点。

**[假设状态]** `_update_hypothesis_status()`累计模型提取的支持/反驳证据；对应方向达到2条后更新supported/refuted。单条支持或反驳不会自动转为partially_supported，其他证据类型可能更新该状态。这是程序计数规则，不代表假设已被严格证实。

**[模型选择]** DeepScout使用qwen-plus，temperature=0.2；Agent基类请求默认max_tokens=16000，具体请求可覆盖。输出上限不能保证JSON完整或响应必然成功。

**\[SSE事件流\]**    research\_step（开始、完成搜索），action（Agent动作），search\_progress（搜索进度），search\_results（搜索结果），observation（观察结果），thought（思考过程）

## \[M02\-T04\] \[Agent \- DataAnalyst\]

**\[职责\]    **从文本（搜索结果）中提取结构化数据点、构建实体关系知识图谱（nodes \+ edges）、生成 ECharts 图表配置（JSON）【这里仅生成配置，不执行代码】、识别数据趋势和洞察

**\[Prompt设计\]  ：**DATA\_EXTRACTION\_PROMPT（从文本中提取结构化数据），KNOWLEDGE\_GRAPH\_PROMPT（构建知识图谱），CHART\_GENERATION\_PROMPT（生成ECharts图表配置）图表类型选择规则 ：时间序列数据 → `line` （折线图）；分类比较数据 → `bar` （柱状图）；占比分布数据 → `pie` （饼图）；进度/百分比 → `horizontal_bar` （横向进度条）；多维对比 → `radar` （雷达图）

**\[核心实现\]：**

1. process\(\) 入口

2. \_analyze\_data\(\) \- 数据分析流程：发开始事件 → 提数据 → 建图谱 → 生成图表 → 推图谱/图表事件 → 发完成事件

3. \_extract\_data\(\) \- 数据提取：取前 20 条事实格式化 → 拼 Prompt → LLM 提取 JSON → 数据点/洞察写回 state → 返回结果

4. \_build\_knowledge\_graph\(\) \- 知识图谱构建：取前 15 条事实（试出来的，太多了知识图谱输出太长太杂，效果反而不好）→ 拼 Prompt → LLM 提取实体和关系（nodes和edges） → 根据重要性（默认为5）算节点尺寸（根据公式 `size = 20 + importance * 3`计算出大小，最小23，最大50） → 返回图谱。

5. \_generate\_charts\(\) \- ECharts 图表生成：准备数据（从extracted\_data中去除三类数据：数据点，事件序列，分布，再加上state\["data\_points"\]中已有的前10条数据点作为补充） → 数据量校验，没数据就跳过 → LLM 生成 ECharts 配置 → 补全图标的唯一 ID → 返回图表列表

**[模型选择]** DataAnalyst使用deepseek-v3.2，数据提取与图谱分析temperature=0.2，图表配置temperature=0.3；Agent基类默认max_tokens=16000。

**\[SSE事件流\]**    research\_step（开始、完成分析），knowledge\_graph（知识图谱），charts（图表配置）

## \[M02\-T05\] \[Agent \- CodeWizard\]

**\[职责\]   ** 唯一有权执行Python代码的Agent，负责数据清洗（统一不同来源的数据口径），统计分析\(计算关键指标（CAGR（年复合增长率）、同比等）\)，预测建模（简单的趋势预测），专业绘图（生成高质量数据可视化（PNG图片））

**\[Prompt设计\]  ： **

1. ANALYSIS\_PROMPT（生成数据分析代码）

    - 禁止使用反斜杠续行 ： `\` 导致 "unexpected character after line continuation character" 错误

    - 数据精简 ：只选取最关键的 5\-10 个数据点

    - 列字典格式 ： `data = {"Year": [2020, 2022], "Value": [100, 200]}`

    - 代码长度 ：不超过 40 行

    - 禁止 import ：已预导入 pd, np, plt, sns

    - 高级样式 ：seaborn 主题、专业配色、高 DPI

2. CHART\_PROMPT（生成特定类型图表的代码）：支持折线、柱状、饼图、散点图、热力图

3. CODE\_FIX\_PROMPT（修复执行失败的代码）

    - `could not convert string to float` → 使用 `pd.to_numeric()` 清洗数据

    - `SyntaxError` → 检查反斜杠、括号

    - `KeyError` → 检查列名

    - `TypeError` → 类型转换

**\[核心实现\]：**

1. process\(\) 入口：`phase == ANALYZING`或 `data_points >= 3`才进入分析 → 调用 `_analyze_data` 做全套分析 → 图表生成→ 返回状态。

2. \_analyze\_data\(\) \- 数据分析：取数据点，格式化 → 拼接Prompt，LLM 生成分析代码 → 清理代码 → 执行（出错自愈）→ 收集图表并逐个推送。

3. `_execute_in_sandbox()`保留原方法名，但实际为同进程受限exec：检查模块与危险代码模式，设置绘图环境，捕获stdout/stderr，并在绘图锁内收集本次所有新建图形、转换Base64后关闭。

    1. 仅开放pandas、numpy、matplotlib、seaborn等选定模块。

    2. 禁止直接调用open、exec、eval、os、sys、subprocess等危险名称。

    3. 检查requests、urllib、socket等直接网络调用；以上限制不能阻止所有间接文件/网络访问，不是进程、文件系统或网络隔离。

    4. **非交互式后端 **： `matplotlib.use('Agg')` ，不弹窗

    5. 中文字体预设：配置候选字体；实际效果取决于运行环境安装的字体。

4. \_execute\_with\_self\_correction\(\) \- 带自愈的执行：循环执行代码（最多重试 3 次） → 成功就返回（包含输出、图表、重试次数和最终代码的结果字典） → 失败，取出error和stdout，就让 LLM 分析错误并修复 → 修复后再执行，若循环结束仍未成功返回失败。

5. \_clean\_code\(\) \- 清理 LLM 输出：用于修复LLM生成代码中的格式问题，LLM可能输出：反斜杠续行；转义的 \\n；LaTeX 风格换行；语句粘连。对此清理策略为：去 Markdown 代码块标记→ 正常代码直接逐行 `rstrip` 去尾空格并返回 → 定义占位符保护字符串内 `\n` → 替换各种假换行为真换行 → 修复语句粘连（用正则匹配“前一句的结尾符号（`]`、`)`、`"`、`True`、`False`、`None`）”后面紧跟“下一句的开头（`plt.`、`fig =`、`ax.`、`df =`）”的情况，在中间插入换行符。） → 从多到少处理多重转义的 `\n` → 恢复占位符保护的正常`\n` → 移除 import/rcParams/续行符 → 返回。

6. \_save\_debug\_log\(\) \- 单步调试：首次调用建时间戳目录 → 每个步骤写一个独立文件 → 记录时间/长度/内容。

**[模型选择]** CodeWizard使用deepseek-v3.2，代码生成temperature=0.3，修复temperature=0.2；Agent基类默认max_tokens=16000。

**\[SSE事件流\]**    code（生成的代码），code\_result（执行结果），code\_fix（自愈修复），chart（生成的图表）

**[执行限制]** 黑白名单检查直接危险操作并开放选定分析模块；同进程exec不能保证阻断所有间接文件或网络访问。强隔离仍需另建容器/进程执行环境。

## \[M02\-T06\] \[Agent \- LeadWriter\]

**\[职责\]   ** 深度写作（撰写有逻辑、有深度的行业分析），Markdown 排版（专业的格式规范），图文混排（整合文字、图表、数据），参考文献（规范的引用格式），两种模式（初稿撰写 vs 审核后修订）

**\[Prompt设计\]  ： **

1. SECTION\_WRITING\_PROMPT（单个章节撰写）

    - 专业性：使用行业术语

    - 逻辑性：论点清晰，论据充分

    - 数据支撑：关键观点必须有数据或事实支撑

    - 引用规范： `[来源名称](URL)` 格式

    - 图表整合： `![图表标题](chart_id)` 占位符

    - 字数控制：500\-1000 字

    - 不重复标题：正文开头不要再写章节标题

2. SYNTHESIS\_PROMPT（整合各章节成完整报告）：撰写报告摘要（Executive Summary），整合各章节，确保逻辑连贯，撰写结论与展望，整理参考文献列表

    - 标题编号规则：1、1\.1、1\.1\.1（不要在正文中重复标题）

    - 引用格式： `[来源名称](URL)` （确保可点击）

    - 报告结构：不使用 `#` 一级标题，直接从"执行摘要"开始

3. REVISION\_PROMPT（根据审核反馈修订报告）

    1. 针对性修改：只修改有问题的部分

    2. 补充来源：对缺少来源的观点补充引用

    3. 修正错误：纠正事实错误或逻辑漏洞

    4. 保持风格：修订后保持报告整体风格一致

**\[核心实现\]：**

1. process\(\) 入口：看阶段 → 是写作就写报告 → 是修订就改报告 → 都不是就跳过

2. \_write\_report\(\) \- 撰写报告：发开始事件 → 逐章节写（跳过已写的）→ 整合完整报告 → 发完成事件 → 切到审核阶段

3. \_write\_section\(\) \- 撰写单个章节：收集事实/数据/图表 \+ 前五条insights→ 拼 Prompt ，调用LLM，temperature=0\.4（允许行文又文采），max\_tokens=16000→ LLM 生成章节内容 → 存草稿 \+ 收集引用 → 推送前端展示。

4. \_synthesize\_report\(\) \- 整合报告：发通知 → 收集章节和来源（合并已收集的参考文献，事实里的来源，并做去重检查，最终最多取前30条来源） → LLM 整合润色 → 成功则存最终报告/失败则手动拼接 → 推送完成事件。

5. \_revise\_report\(\) \- 修订报告：收集未解决问题\(从 `state["critic_feedback"]` 中筛出 `resolved` 为 `False` 的问题，格式化成 `- [严重程度] 问题描述 + 建议`\) \+ 新信息\(取 state\["facts"\] 中最后 5 条（通常是补充搜索新增的事实），每条截取前 200 字符，防止太长。\) → LLM 修订报告\(原报告内容截取前6000字符与反馈列表\+新信息填入Prompt模板，temperature=0\.3，max\_tokens=16000\) → LLM返回`revised_content`（修订后的报告）、`addressed_issues`（已解决的问题 ID 列表）、`changes_made`（修改点）、`unable_to_address`（无法解决的问题）→ 更新报告 \+ 标记已解决问题 → 切回审核阶段。

**\[初稿模式与修订模式对比\]**

|特性|初稿模式|修订模式|
|---|---|---|
|触发阶段|WRITING|REVISING|
|输入|事实、数据、大纲|原报告 \+ 审核反馈 \+ 新信息|
|处理流程|逐章节撰写 → 整合|直接修订全文|
|temperature|0\.4（更有创造性）|0\.3（更保守）|
|输出|完整报告草稿|修订后的报告|
|更新状态|draft\_sections \+ final\_report|只更新 final\_report|

**\[模型选择\]：**deepseek v3\.2，温度0\.4（初稿），max\_tokens=16000

**\[SSE事件流\] **    research\_step（开始/完成写作），thought（思考过程），action（Agent 动作），section\_content（章节内容），report\_draft（报告草稿），revision\_complete（修订完成）。

**\[引用规范化\]     **

1. 收集引用来源：从两个地方汇总参考文献。一是从各章节写作结果里提取 LLM 返回的 `citations`，存入 `state["references"]` 并自动编号；二是从事实库（`facts`）里补充来源，做去重后加入 `all_sources` 列表。

2. 引用结构：Writer初始保存id、marker、source、url；后续结果可能补充title、link、content等展示字段。并非每条来源都有作者、日期或完整元信息。

3. 前端按实际可用的标题、链接和来源展示引用，缺失字段不虚构。引用仍需用户核对原始出处。

## \[M02\-T07\] \[Agent \- CriticMaster\]

**\[职责\]   ** 

1. **按任务与证据质检**：不预设报告有问题；区分现实事实、用户提供数据和已声明的合成算例。来源、计算、图表或外推确有错误时仍需指出，不为满足角色而制造缺陷。

2. **逻辑漏洞检测 **：检查推理链条是否严密

3. **幻觉查杀 **：识别无来源或错误的信息

4. **偏见识别 **：发现观点偏颇或情绪化表达

5. **智能路由 **：决定下一步是补充搜索还是仅修改文字

6. **质量评分：**模型给出五个维度的辅助评分，程序按权重计算总分；分数仍是模型评估，不代表事实核验已经全部完成。

**\[Prompt设计\]  ： **

1. REVIEW_PROMPT：审核当前报告，输出五个1—10分维度和有证据的问题列表；总分由后端按既定权重计算，至少7分且无critical/major问题才通过。

    1. **来源与范围**：用户提供的数据及明确标注的合成样本是限定任务的合法输入；不能据此宣称现实市场事实。

    2. **逻辑与计算**：核对论据、计算、图表与结论是否一致，不忽略真实错误。

    3. **客观性**：样本有限、未外部核验等诚实说明不是偏见；不得强行制造负面评价。

    4. **时效性**：按任务要求判断，正确标注的历史分析或合成数据不因年份较早自动成为错误。

    5. **完整性**：以用户问题和大纲为边界，不强求未要求的外部研究；无真实问题时允许issues为空。

2. FINAL\_CHECK\_PROMPT（修订后再次审核，最终质量把关）

    - 检查之前的问题是否已解决

    - 是否有新问题产生

    - 给出最终评语

**\[核心实现\]  ： **

1. process\(\) 入口：阶段是REVIEWING，发送开始通知，\_review\_content\(state\)审核报告 → 返回审核结果（问题列表，总体评估等） →  遍历审核发现的问题，为问题生成唯一ID标记resolved=False，追加到state\["critic\_feedback"\] ,更新 `state["quality_score"]`（质量分数）和 `state["unresolved_issues"]`（未解决的严重问题数）。推送 `review` 事件，包含：审核结论、质量分、问题总数、严重/重要问题数、摘要、缺失的方面。  → 根据结论智能路由:

    - `pass`（通过）：直接进入 `COMPLETED`（完成阶段）。

    - 达到最大迭代次数：强制进入 `COMPLETED`，并推送警告“部分问题可能未解决”。

    - 否则（需要修改）：调用 `_analyze_issues_for_routing` 判断问题类型：

        - 需要补充搜索（信息缺失）：切到 `RE_RESEARCHING` 阶段，并把待搜索问题写入 `state["pending_search_queries"]`。

        - 只需文字修改：切到 `REVISING` 阶段。

        - 最后 `state["iteration"] += 1`，累计迭代次数。

2. \_analyze\_issues\_for\_routing\(\) \- 智能路由：从审核结果中取出issue问题列表和missing\_aspects缺失的方面，看问题类型（缺来源/不完整/过时）\+ 看严重程度（critical/major需要\+1）→ 如果问题明确要求重新搜索（`requires_new_search`）并提供了搜索词（`search_query`），就把搜索词加入 `search_queries`。→ 补充遗漏方面的搜索词，遍历 `missing_aspects` 的前 3 条，把它们也作为搜索词加入。→ 满足以下所有条件时，需要补充搜索：有搜索词（`len(search_queries) > 0`）；有需要搜索的严重问题，或有遗漏的方面；要么没有严重问题，要么“需要搜索的严重问题”占比超过 30%。→最后返回 `{"should_research": bool, "search_queries": [去重后的最多5个查询]}`。

3. `_review_content()`优先读取当前final_report，缺失时回退draft_sections；结合前20条事实、前15条数据和大纲调用模型审核。报告最多取8000字符，因此超长报告的尾部不属于本轮全文审核覆盖范围。

**\[6类问题类型\]     **missing\_source（缺少来源），logic\_error（逻辑错误），bias（偏见），hallucination（幻觉），outdated（过时），incomplete（不完整）

**[质量评分机制]** 模型先核对事实和计算，再列问题，最后提供source_completeness、logical_rigor、objectivity、timeliness、completeness五个1—10分维度；后端严格拒绝布尔值、缺项、非数字、非有限及越界值，按0.3、0.3、0.2、0.1、0.1计算唯一总分，不采用模型自报总分。若事实核查含false/suspicious而issues没有critical/major问题，不能直接判为通过。输出校验失败仅纠正重试一次，反馈错误字段、原值/类型和上次回答，要求按证据重新评估，禁止机械截断、取绝对值、缩放或补分。审核请求绕过缓存。仍失败时保留报告、清除旧评分并提示“审核待确认”；模型分数不等于独立事实核验。

**\[决策逻辑\]**

1. 当前asyncio流程由Critic更新phase决定后续：需要新证据进入补检，需要修改进入修订；不是仅依据未解决问题数量调用通用_should_revise。

2. SSE事件流：thought（思考过程），review（审核结果），critic\_feedback（具体问题 critical 级别），warning（警告信息）。

3. max_iterations默认3，接口允许1—5，限制修订循环次数；初始审核后仍可按预算修订并复审，不能把该参数当成所有审核调用总数。达到上限时输出警告并保留报告，不把达到上限当成质量通过。

4. 有效评分至少7分且没有critical/major问题时通过；否则在迭代预算内补检或修订，再次审核。达到上限时携带警告完成，用户仍需查看未解决问题。

**[模型选择]** Critic默认使用qwen-plus，可通过CRITIC_MODEL覆盖；temperature=0、max_tokens=16000，审核请求不读写共享LLM缓存。模型与参数选择不能替代结构和数值校验，评分阈值与权重保持不变。

## \[M02\-T09\] \[记忆层实现\]

**\[记忆层架构\]  **

1. 用户对话

2. 短期记忆：消息存入ChatMessage后登记待处理会话，以cl100k_base估算未压缩文本token；默认达到10000时触发后台压缩。只登记启用后保存的新消息，不扫描所有历史会话。

3. 记忆压缩：默认qwen-plus，每批最多30000字符，生成summary、key_insights、user_preferences和topics；保存消息ID及字符进度，只推进成功部分，尾部等待后续批次。没有95%的固定压缩率。

4. 长期记忆：当前用户范围内进行关键词与向量融合召回，按memory_id去重、经PostgreSQL再次核验归属。聊天上下文默认取Top-3；`/memories/search`默认Top-5，可传1—20。

    1. PostgreSQL存储结构化摘要、洞察、主题及来源进度；原始对话仍在消息表，不是复制进记忆表。关键词查询使用参数化SQL。

    2. Milvus存储摘要、洞察与主题向量；向量不可用时关键词结果仍可用。使用排序融合，不把余弦分数与关键词分数直接相加。

**\[核心概念\]     **

|特性|短期记忆（Working Memory）|长期记忆（Long\-term Memory）|
|---|---|---|
|存储位置|PostgreSQL消息与请求上下文|PostgreSQL摘要 + Milvus向量|
|生命周期|会话消息持久保存，调用时选取预算内上下文|持久保存，受用户删除及存储策略影响|
|容量限制|受消息条数与上下文token预算限制|受磁盘、数据库容量及成本限制|
|访问方式|按预算组织最近消息|当前用户的关键词与向量融合召回|
|内容|原始消息与本次上下文|摘要、洞察、主题、偏好和处理进度|

触发方式：界面“保存为记忆”、新消息达到token阈值、每30分钟检查已登记且有未处理消息的会话。三者共用增量压缩逻辑，以会话锁避免重复。自动队列对摘要失败有限重试；手动模型失败返回503，用户可重新提交。摘要成功后单独提交向量索引任务，失败时保留摘要并重试索引，不伪装为完成。

**\[核心实现\]**

1. 记忆总结：按来源消息进度组织未压缩内容，每批最多30000字符，调用模型并校验结构；成功摘要先保存再推进进度，失败按策略重试。没有单次0.05元的固定费用保证。

2. 记忆向量化：创建COSINE索引，为摘要、每条洞察及组合主题生成向量，使用基于memory_id的稳定ID进行Milvus upsert；索引失败保留PostgreSQL摘要并重试。

    1. 向量化策略：摘要整体向量化（用于召回整个对话摘要），每条洞察独立向量化（精细粒度检索），主题列表组合向量化（主题匹配）

    2. 为什么分开向量化：提高检索精度（可以匹配到具体洞察），支持多粒度召回（整体摘要\+具体细节），灵活的相关性计算。

3. `MemoryService.retrieve_memories()`：查询当前用户关键词结果，同时按用户过滤检索Milvus；对结果进行排序融合，按memory_id去重并通过PostgreSQL再次验证归属后返回。

4. 记忆上下文构建：检索相关记忆 → 去重 → 构建上下文（格式化为文本）→ 根据类型添加前缀

**\[实战应用\]**

1. 自动压缩：仅对功能启用后登记的新消息检查阈值，通过后台任务压缩，不扫描历史全部用户消息。

2. 上下文召回：按当前用户融合关键词与向量结果，去重后按预算注入模型上下文。

3. 偏好利用：从摘要中提取user_preferences并在相关问答中作为上下文参考；没有修改模型权重，没有Fine-tuning训练，也不保证永久学习。


# [A01] 代码对齐版补充说明

本版以项目实际代码和功能测试为准。本文中的调用流程和JSON示例用于解释结构，不代表每次模型调用都会产生相同章节、图表数量、评分或耗时。

## 新增功能与运行约束

- 知识库：支持搜索、相关段落高亮、余弦及重排分数、鉴权原文件下载。新上传原件保留在`backend/storage/knowledge`；`KNOWLEDGE_STORAGE_DIR`可指定其他目录。原件随文档或知识库删除。历史原件若已被旧版清理，无法凭向量恢复。
- 附件：TXT/Markdown/常用文本本地读取，文字PDF、DOCX、XLSX优先本地提取；图片、扫描PDF、DOC/XLS/PPT/PPTX通过已配置的DocMind解析。WebP先本地转PNG。图片最多20MB，其他附件最多100MB；正文最多保留50000字符并提示截断。服务不支持的内容或空解析结果会明确失败，不返回文件名占位正文。
- Markdown：代码高亮、行内/块级数学公式、GFM表格和图片懒加载。公式渲染不执行可信HTML扩展，最终HTML经DOMPurify过滤。
- Text2SQL：模型使用动态读取的三张行业表结构；表格始终可用，图表仅在数据和visualization_hint适配时展示。
- 研究：已鉴权用户可读取自己的检查点、取消和继续研究。每用户同时最多一项，每分钟最多启动/恢复10次；同一会话重复运行被拒绝。断流后从阶段检查点手动继续，未完成阶段可能重做。
- 质量审核：默认使用qwen-plus，先核对事实与计算，再列问题和评分；总分由后端严格按五维权重计算。校验失败最多纠正一次，不补造分数；即使总分达到7，有critical/major问题仍需修订。
- 记忆：手动保存与新消息自动任务共用增量处理逻辑。摘要先保存在PostgreSQL，向量失败时保留摘要并重试索引，关键词召回仍可用。长输入按批次推进，不把截断尾部直接标记为已处理。

DocMind图片默认启用VLM版面/OCR增强并保留页眉页脚；合成图片已真实识别成功。增强模式可能增加耗时和每页费用，可用`DOCMIND_IMAGE_VLM_ENABLED=false`关闭。格式和计费说明参考[官方文档解析接口说明](https://help.aliyun.com/zh/document-mind/developer-reference/document-parsing-large-model-version)。这里列出本项目接入的路径；不保证任意损坏、加密或特殊排版文件均可识别，也未逐一验收全部格式。

重排默认模型已更新为`qwen3-rerank`，真实调用成功。原默认`gte-rerank`已于2026-05-30下线，相关403不能直接判定为余额不足。[官方模型说明](https://help.aliyun.com/zh/model-studio/rerank)

## 自动记忆与缓存配置

不需要修改现有`.env`即可使用默认值。自动任务会调用已配置的模型和向量服务，产生正常API用量；只处理功能启用后登记的新消息，不主动压缩全部历史会话。

|变量|默认值|作用|
|---|---|---|
|MEMORY_AUTO_ENABLED|true|开启新消息自动记忆；false保留手动保存|
|MEMORY_TOKEN_THRESHOLD|10000|超过阈值后触发后台压缩|
|MEMORY_INTERVAL_MINUTES|30|定期检查待处理新消息的间隔|
|MEMORY_MAX_RETRIES|3|总尝试次数上限，包含首次尝试|
|MEMORY_JOBS_PER_RUN|5|每轮最多5个压缩任务和5个索引任务，各自上限20|
|MEMORY_VECTOR_ENABLED|true|开启记忆向量化及向量召回|
|MEMORY_CONTEXT_ENABLED|true|在当前用户聊天中注入相关记忆|
|MEMORY_MODEL|qwen-plus|记忆摘要模型|
|EMBEDDING_CACHE_TTL_SECONDS|86400|共享Embedding函数的缓存秒数，0关闭|
|RERANK_MODEL|qwen3-rerank|当前可用的重排模型|
|CRITIC_MODEL|qwen-plus|独立配置质量审核模型，保留五维量表与权重|
|DOCMIND_IMAGE_VLM_ENABLED|true|图片使用VLM增强；可能增加云端用量和耗时|
|CORS_ALLOW_ORIGINS|http://localhost:5183,http://127.0.0.1:5183|允许的浏览器来源，以逗号分隔|

记忆阈值使用cl100k_base编码统计作为统一估算，不等同于模型服务商计费token。研究搜索缓存为15分钟，研究非流式LLM成功响应缓存为1小时；质量审核Critic及其纠正请求绕过该缓存，避免复用未通过业务校验的评分。缓存键包含相应模型、参数及用户/账号范围。Embedding缓存只存向量和散列键，不存明文原文。

## 尚未实现或尚未验收

1. Fine-tuning训练、科研文献专用平台和完全离线部署，需要独立数据、模型、硬件与产品设计；当前记忆属于摘要及上下文利用。

4. 完整多租户数据权限、历史知识库集合迁移、HttpOnly Cookie/CSP、微服务及集群运维，需明确权限规则和部署方案后实施。新增的研究、附件和知识库归属校验不代表所有历史路径已生产化。

6. 200—300/数千并发、百万向量小于100ms、95%压缩率、固定单次成本以及7×24可靠性均不是已验证指标。
7. 所有文件格式/OCR质量、真实批量新闻与招投标采集、长时间负载及完整攻防未做全面验收。
